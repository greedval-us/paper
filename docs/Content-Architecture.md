# Каталог контента и баланс

Техническая справка по действующим системам игры. [Эскизы и целевой дизайн](Game-Design.md) задают визуальный ориентир; [статус переноса в Unity](Implementation-Roadmap.md) отделяет реализованные экраны от оставшейся работы.

Основания, оружие, оборудование, заготовки рисунка и варианты существующих атак задаются записями `ContentDatabaseAsset`. Рабочий пресет объединяет эту базу с глобальными правилами. Добавление детали с уже поддерживаемым поведением не требует нового enum, кнопки HUD или ветки по её ID. Свободный рисунок добавляет геометрические множители поверх выбранных деталей; правила этого расчёта также принадлежат каталогу.

Этот документ описывает источник данных и порядок расширения. [Реестр механик](Current-Mechanics.md) показывает текущий состав, [общая архитектура](PaperDefense-Architecture.md) объясняет слои, [контракты механик](Mechanics-Contracts.md) — отключение необязательных систем, [совместимость профиля](Content-Profile-Compatibility.md) — миграцию и защиту сохранений.

Цепочка подготовки: `GameBalanceAsset.dataPreset` → `BalancePresetAsset.CreateBalance()` → копия `GlobalBalanceSettings` → копия каталога → полные переопределения → `ContentCatalogSnapshot` → проверенный `GameBalance` → партия, мастерская и полигон.

`presets` у базы — список связанных пресетов для проверки Inspector. Активный пресет задаёт ссылка `GameBalanceAsset.dataPreset`; порядок массива `presets` ничего не выбирает. Основная сцена использует PlayerBalance; Historical/Target остаются для редакторских инструментов и тестов.

Снимок каталога владеет своими вложенными коллекциями. `GameSession`, `WeaponSystem` и `TrialRunner` подготавливают правила на границе запуска. Read model отдаёт интерфейсу подготовленные данные. Изменение исходного asset не меняет уже начатый бой, цели, снаряды или записанное испытание. Поиск по ID, разрешение сборки, оценка и геометрия кэшируются; каталог не собирается заново каждый кадр.

У мигрированных assets `legacyAuthoringAdapter=false`: потерянная ссылка на `dataPreset` вызывает ошибку. `LegacyContentCatalog`, `PartCatalog`, исторические фабрики и числовые поля остаются адаптерами старых сохранений и явных fixtures. Новые записи добавляются в базу. Для запуска `RunController` нужен назначенный asset; разрешение legacy defaults в изолированных fixtures задаётся явно.

## Приоритет и полное переопределение

1. Глобальные правила берутся из активного `BalancePresetAsset.rules`.
2. Базовые записи деталей, эффектов и рисунков берутся из `database.catalog`.
3. `overrides.Chassis`, `Weapons`, `Modules`, `Effects`, `Templates` заменяют **целую запись с тем же ID**.
4. Конечный кандидат проходит проверку до публикации и запуска. Старые поля `Construction`/`Effects` заполняются совместимой проекцией уже разрешённого каталога.

Отсутствие override-записи означает наследование базы. `0`, `false`, пустой список и пустая допустимая строка внутри override — собственные значения полной записи. Они не означают «наследовать поле». Перед изменением одного параметра скопируйте всю базовую запись в соответствующий override и измените нужное поле. Иначе незаполненные поля получат собственные нулевые значения или вызовут ошибку.

Повтор одного ID в базе или в одном списке overrides запрещён. Override неизвестного ID запрещён: новый элемент регистрируется в базе. Порядок записей overrides не задаёт приоритет. `StartingPages`, цветные привязки, `Assessment`, `FreeformRules` и `DrawingUnlocks` принадлежат базе; их отдельного механизма overrides сейчас нет. Сами глобальные `rules` каждого пресета задаются полностью. Точный состав замен задаёт [ContentOverrides](../Assets/PaperDefense/Application/ContentDatabaseAsset.cs), глубокую копию — [ContentInputCopy](../Assets/PaperDefense/Core/ContentInputCopy.cs).

## Словарь каталога

Все три категории деталей наследуют общие поля:

| Поля | Смысл |
|---|---|
| `Id` | Постоянный строковый ключ. Не меняется при переименовании, сортировке или правке баланса. |
| `Name`, `Description` | Название и описание в мастерской, альбоме и read model. |
| `ButtonLabel`, `UnlockLabel` | Короткие подписи выбора и постоянного открытия. |
| `Enabled`, `InitiallyUnlocked`, `UnlockGold` | Доступность определения, право нового профиля и цена постоянного открытия в золоте. Открытие не покупает расходуемый экземпляр. |
| `Order` | Порядок UI. Равные значения сортируются по `Id` ordinal. Порядок массива не является идентификатором. |
| `TemplateId`, `VisualStyle` | Ссылка на образец. `Template` отображает его контуры; `Legacy` сохраняет старый стиль канонических исторических деталей. Новый ID использует данные образца. |

ID непустой, без внешних пробелов и управляющих знаков, длиной до128 символов. ID деталей уникален сразу среди оснований, оружия и модулей. Эффекты и образцы проверяются в своих списках. Практичный формат — `chassis.name`, `weapon.name`, `module.name`, `effect.name`, `template.name`.

### Основания: `catalog.Chassis`

| Поля | Смысл / единицы |
|---|---|
| `Capacity`, `BaseCost` | Вместимость нагрузки и стоимость основания в штрихах. |
| `BaseHealth`, `HealthMultiplier` | Базовые HP и множитель до оборудования и материала. |
| `BuildSeconds`, `SecondaryBuildSeconds` | Добавка времени основания и надбавка за каждое занятое крепление сверх первого, секунды. |
| `MountCount` | От одного до трёх креплений с устойчивыми индексами `0..2`; слот 0 обязателен, дополнительные могут оставаться пустыми. |
| `ArmorSlotCount`, `UpgradeSlotCount` | Независимые пределы брони и улучшений; общая нагрузка проверяется дополнительно. |
| `FeedCapacity` | Общая подача основания для `Construction.DynamicFeed`; ноль в старых standalone-определениях использует глобальный fallback. |
| `MountPivots` | Список `SlotIndex`, `X`, `Y`: одна нормализованная опора на каждый слот основания. |
| `PrimaryMountPivotX/Y`, `PrimaryDualMountPivotX/Y`, `SecondaryMountPivotX/Y` | Совместимые опоры первого/второго креплений для старых определений без `MountPivots`. |

### Оружие: `catalog.Weapons`

| Поля | Смысл / единицы |
|---|---|
| `Attack` | Поддерживаемый алгоритм из таблицы ниже. |
| `Load`, `AssemblyCredit` | Нагрузка и вычет из цены этой оружейной детали при сборке. |
| `Stats.Cost`, `MaxHealth`, `BuildSeconds` | Цена детали в штрихах, HP и время постройки. HP собранной башни считается по основанию. |
| `Stats.Range`, `Damage`, `ShotInterval` | Дальность в клетках, урон попадания и исходный интервал в секундах. |
| `MinimumRange` | Внутренняя граница выбора цели, неотрицательная и ниже внешней дальности действующего оружия. Фильтрация применяется до выбора приоритета и расчёта подачи; уже выпущенный снаряд сохраняет свой удар. |
| `Stats.Radius`, `FlightSeconds` | Полуширина/радиус существующей геометрии и время полёта площадного снаряда. |
| `Stats.MaxPierce`, `ConeAngleDegrees`, `MaxTargets`, `JumpRange` | Предел целей линии, угол конуса, конечное число целей и дальность следующего рикошета. |
| `MinimumLineRadius`, `MinimumRadialRange` | Настраиваемые нижние границы геометрии соответствующего алгоритма. |
| `MaximumFootprintAspectRatio` | Предел вытянутости овала либо свободного контура площадного снаряда. Историческое значение3; допустимая техническая граница1–64. |
| `EffectIds` | Список встроенных эффектов попадания из `catalog.Effects`. |

| `AttackKind` | Поведение |
|---|---|
| `Single` | Одна выбранная цель. Замедляющее оружие получается назначением эффекта `Slow`. |
| `Line` | Линейная область с конечным пределом целей. |
| `AreaProjectile` | Снаряд с временем полёта и зафиксированной областью попадания. [Редактор отпечатка](Charge-Imprint.md) поддерживает круг, овал и свободный замкнутый контур постоянной площади. |
| `Cone` | Конус с пределом целей. |
| `Ricochet` | Цепочка соседних целей без повторного поражения той же цели в цепочке. |
| `Radial` | Радиальная область. |
| `Cleanup` | Очистка клякс. Доступность зависит от соответствующей механики. |

Не все поля `Stats` используются каждым алгоритмом. `LegacyKind`, `LegacyModule`, `Stats.Kind` и старые `Stats.Slow*` сохраняются для совместимости. Для нового ID роль определяют `Attack` и `EffectIds`; ему не назначают новое числовое значение `StructureKind`.

### Оборудование: `catalog.Modules`

`Load`, `Cost`, `BuildSeconds` задают нагрузку, стоимость в штрихах и добавку времени. `SlotKind` выбирает отдельный слот `Armor` или `Upgrade`; отсутствие нового поля в старых данных означает `Upgrade`. `Repeatable` разрешает несколько экземпляров одного определения. Каждый экземпляр имеет собственный `InstanceId`. Непустая `ExclusiveGroup` запрещает одновременные экземпляры с той же группой, включая повтор одного модуля.

Пустые `AllowedChassisIds` и `AllowedAttacks` не добавляют ограничений. Непустой список оснований разрешает перечисленные ID. Непустой список атак требует, чтобы атака **каждого установленного оружия** входила в список. Эти условия проверяются вместе с доступностью определений, правами и итоговой нагрузкой.

`Modifiers` содержит типизированные операции:

| Поле | Значения |
|---|---|
| `Stat` | `FoundationHealth`, `FoundationDefense`, `WeaponRange`, `ActionInterval`, `FeedMultiplier`, `AcquisitionSeconds`. |
| `Operation` | `Set`: заменить; `Add`: прибавить; `Multiply`: умножить. |
| `Scope` | `Foundation`: основание; `AllWeapons`: общие оружейные параметры; `Mount`: выбранное крепление; `Support`: сервисное оружие `Cleanup`. |
| `MountIndex` | 0, 1 или 2 при `Scope=Mount`. |
| `Value` | Значение в единицах выбранной характеристики. Для `Multiply` это множитель. |

Здоровье и защита основания требуют `Scope=Foundation`; остальные характеристики используют оружейные области. Модификаторы применяются **в порядке экземпляров `TowerBlueprint.ModuleSelections`, затем в порядке `Modifiers` каждого определения**. `Order` каталога влияет только на UI. Операции не переставляются: `Set` после `Multiply` заменит уже умноженное значение. Поэтому порядок установки и список операций должны быть осмысленными.

Здоровье сначала получает базовый множитель основания, затем оборудование, затем материал и геометрию свободного корпуса. Дальность свободного ствола получает геометрический множитель перед оборудованием и поиском цели. Геометрический множитель интервала применяется перед делением на подачу; модификаторы оборудования — после. Конечная граница интервала задаётся `Combat.MinimumActionInterval`; художественная точность больше не снижает темп. Общая подача считается один раз для башни. Scope крепления различает одинаковые орудия по индексу, а не по их ID. Формулы находятся в [TowerCatalog](../Assets/PaperDefense/Core/TowerCatalog.cs).

### Эффекты: `catalog.Effects`

Запись содержит `Id`, `Kind`, `Duration`, `Strength`, `TickSeconds`, `IgnoresDefense`. Поддержаны `DamageOverTime` (урон `Strength` за тик), `Slow` (множитель скорости `Strength`) и `DefenseReduction` (доля снижения защиты). Время задаётся секундами. Для урона за время `TickSeconds` положителен; сила замедления и снижения защиты находится в0–1.

`RedEffectId`, `BlueEffectId`, `GreenEffectId` базы связывают существующие цветные каналы соответственно с уроном за время, замедлением и снижением защиты. Встроенные `Weapon.EffectIds` отдельны от платного цветного картриджа. Общие пределы защиты, бюджет и окно цвета находятся в `rules.Effects`.

### Стартовые страницы: `catalog.StartingPages`

Для нового профиля запись задаёт `Id`, `Name`, `ChassisId`, список `WeaponMounts` с `SlotIndex`/`WeaponId`/`FootprintAspect`, список `Modules` с `InstanceId`/`DefinitionId` и `Slot`. Непустой `WeaponMounts` задаёт индексированный состав; для старых записей с пустым списком читаются `FirstWeaponId` и необязательный `SecondWeaponId`. `Slot=-1` добавляет страницу только в альбом;0–3 назначают один из четырёх слотов. Повтор одного слота запрещён. Снимок предоставляет `StartupBlueprints` и `StartupSlotIds`.

Пустой список означает пустой новый альбом и неназначенные слоты. Запуск партии требует заполнить комплект доступными страницами. Изменение стартового набора не возвращает удалённые пользователем страницы в существующий альбом. Новые начальные права могут добавляться при подготовке; прежние открытия не отзываются.

## Глобальные правила пресета

| Группа `rules` | Содержимое |
|---|---|
| Основные поля | Размеры листа, здоровье базы, таймеры, стартовые штрихи, доход, награды, параметры ручной очистки и чернильниц. |
| `Mechanics` | Developer-флаги необязательных систем. Игрок не получает переключателей. |
| `Construction` | Общая и динамическая подача, захват цели, пределы подачи и цена цвета. |
| `Effects` | Прорисовка врагов, общий предел защиты и бюджет цветных попаданий. |
| `Progression` | Общие улучшения партии, их периодичность и возврат. |
| `Combat` | Общие числовые границы интервалов, контакта, спавна, движения и поиска. |
| `Battlefield`, `WaveHealthGrowth` | Режим карты, дороги, входы, участки баррикад, непроходимый декор и рост HP по индексу волны. |
| `Crowd` | Распределение спавнов по входу, размеры врагов, локальное расхождение, память направления и зазор препятствий. |
| `MaterialDefinitions`, `EnemyDefinitions`, `Waves` | Параметры существующих материалов/ролей врагов, состав волн и выплаты. `InkGrant=-1` использует общую выплату,0 — явную нулевую выплату. |
| `WellPlacements` | Цвет, дробные координаты относительно размера листа и резервная область чернильниц. |
| `StructureDefinitions` | Непосредственные инструменты `Wall`, `Spikes`, `TarPit`, `RepairPost`. Оружейные детали мастерской находятся в каталоге. |
| `Trials` | Состав существующих полос, бюджеты, шаг, длительность, позиции, кляксы, обратный огонь и `BaselineChassisId`/`BaselineWeaponId` сравнения. |

`TrialRules.Scenarios` настраивает четыре существующие роли испытаний: толпа, быстрые, защищённые, кляксы. `BudgetChoices` содержит уникальные бюджеты и включает `DefaultBudget`. Условия полигона не подменяют параметры обычной партии. Preview, стоимость, строительство и настоящий бой используют общие определения и формулы `TowerCatalog`/`WeaponSystem`.

Состав глобальных полей подтверждается [GlobalBalanceSettings](../Assets/PaperDefense/Application/GlobalBalanceSettings.cs). Параметры карты описаны в [защите листа](Tower-Defense.md), движения — в [движении толпы](Crowd-Movement.md).

## Функциональный рисунок и заготовки

`catalog.FreeformRules` задаёт опорные размеры, минимальную площадь корпуса, минимальную длину и выступание дула, коэффициенты HP/нагрузки/цены/времени/оружия и бюджет геометрических чернил. [FreeformGeometry](../Assets/PaperDefense/Core/FreeformGeometry.cs) измеряет связные группы штрихов корпуса и каждого занятого крепления; [FreeformTowerDesign](../Assets/PaperDefense/Core/FreeformTowerDesign.cs) использует правила v2 для новых рисунков, сохраняя чтение v1. В v2 ствол измеряется только перед креплением. Повторное обведение, подразделение линии и декор не добавляют массу. Полнота, лимит геометрических чернил и допустимая нагрузка проверяются перед сохранением страницы, испытанием и строительством. Это отдельный лимит конструкции, не запас штрихов партии. Подробные формулы — в [параметрах](Balance-Parameters.md), рабочий процесс — в [свободных башнях](Freeform-Towers.md).

`catalog.DrawingUnlocks` содержит `Id`, `Name`, `Description`, `GoldCost`, `InitiallyUnlocked`, `Role` (`Body`/`Barrel`) и `Contours`. Контуры проходят те же проверки координат, что образцы, и должны давать пригодную геометрию своей роли. ID заготовок уникальны и не пересекаются с ID деталей. Их порядок сохраняется по списку базы; `Order`, `Enabled` и overrides для заготовок отсутствуют. Покупка даёт постоянное право вставлять геометрию, а характеристики зависят от получившихся линий.

Рабочая база содержит `drawing.body.basic` и `drawing.barrel.basic` с начальным правом, а также `drawing.sniper` (32 золота), `drawing.rapid` (24) и `drawing.heavy` (40). Открытия хранятся в общем `WorkshopProfile.Unlocked`; транзакцию покупки публикует `RunController` после успешной записи кандидата. Изменение коэффициентов не меняет сохранённые линии, но при использовании сборки применяются текущие правила каталога; версия алгоритма `FreeformRuleVersion` сохраняется отдельно.

## Рисунок, визуал и сохранённая оценка

`catalog.Templates` содержит `Id`, `Revision`, `DisplayName`, `PivotX/Y`, `Weight`, список `Contours` с точками `X/Y`. Координаты локальны для части, находятся в−1…1; направление +Y соответствует направлению оружия. Опора образца используется основанием и модулями, опоры креплений — настройками основания. Контуры одновременно дают образец редактора и визуальную геометрию стандартного нового контента. Отдельного импорта произвольного спрайта в этом срезе нет.

`catalog.Assessment` задаёт `Revision`, `Tolerance`, `CompletionThreshold`, `PrecisionThreshold` для исторических страниц `PlayerDrawing`. Вес берётся из образца; декор не оценивается. Сетка128² относится к архивному сопоставлению с эталоном. Свободный рисунок `Origin=Freeform` получает совместимую оценку100 без сопоставления и обратной связи точности. Квантование координат1/4096 и пределы хранения общие. Геометрия свободного рисунка меняет характеристики корпуса/стволов; область площадного снаряда задаётся отдельно `MortarFootprint`.

Привязки сохраняются независимо от списка каталога:

| Binding | Назначение |
|---|---|
| `base` | Основание. |
| `mount.0`, `mount.1`, `mount.2` | Отдельные слои трёх креплений, включая одинаковые орудия и разреженный состав 0+2. |
| `module.<InstanceId>` | Конкретный экземпляр оборудования. Два экземпляра одного определения имеют разные линии. |
| `decoration` | Общий декор. |

Восемь прежних ключей0–7 сохраняют точное значение и порядок: основание, два крепления, броня, подача, наведение, декор, направляющая. Рисунок только с этими ключами остаётся форматом2 / binding1; формат1 с семью ключами читается с пустой направляющей. Новые bindings, включая `mount.2`, записываются форматом3 / binding2. Сортировка новых деталей не переносит линии между частями.

При смене основания или оружия очищается только его binding. Модуль сохраняет линии при совпадении `InstanceId` и `DefinitionId`; декор сохраняется. Undo/redo относится к частной сессии редактора, Apply переносит рисунок в черновик, запись страницы остаётся отдельной командой профиля.

`DrawingEvaluationStamp` исторической страницы сохраняет версию правил, сигнатуру образцов и допусков, хеш рисунка и состава, качество и обратную связь по bindings. Изменение asset не пересчитывает такую оценку молча: она остаётся архивной. Переименование, копия страницы и подключение актуального каталога сохраняют её. Реальное изменение линий или состава создаёт оценку по актуальным данным. Старые профили оцениваются по архивному legacy-правилу при миграции. При явном переходе в `Freeform` используются геометрические правила и оценка100 с сигнатурой `freeform.v1`; архивное качество не ограничивает бой ни для одного происхождения. Эти ветви разделяет [DrawingEvaluator](../Assets/PaperDefense/Core/DrawingAssessment.cs). Будущая версия схемы DTO защищает источник от перезаписи.

## Добавление контента в Inspector

1. Откройте `PlayerBalance.asset` и его `PlayerRules.asset`/`PlayerContent.asset` для изменения основной игры. Для отдельного сравнения Target/Historical выберите соответствующую базу `NotebookContent.asset`. Не смешивайте эти цепочки.
2. В нужном списке `catalog.Chassis`, `Weapons` или `Modules` добавьте запись либо скопируйте подходящую. Задайте новый постоянный `Id`, названия, описание, доступность и `Order`. Поля `Legacy*` предназначены только историческим адаптерам.
3. Назначьте существующий `TemplateId` или добавьте образец в `Templates`. Для другого внешнего вида используйте отдельный ID образца. Укажите `VisualStyle=Template` для нового оформления.
4. Для оружия выберите поддержанный `Attack`, задайте характеристики, `MinimumRange` и `EffectIds`. Для оборудования задайте стоимость, `SlotKind`, ограничения и `Modifiers`. Для основания задайте нагрузку, слоты, здоровье, подачу и опоры креплений.
5. Если деталь должна отличаться только в одном пресете, скопируйте полную базовую запись в соответствующий `overrides` этого пресета, сохранив ID.
6. Выполните Inspector-команду «Проверить каталог и связанные пресеты», затем проверку нужного пресета. Общая команда — `Paper Defense > Content > Validate all databases and presets`. Ошибка называет запись и поле; неверная конфигурация не заменяется первым известным оружием.
7. Запустите новую подготовку мастерской. Запись появляется в каталоге с прокруткой, открытиях, редакторе и предпросмотре; сохранённая страница использует те же ID в альбоме, полигоне, строительстве и бою. Для проверки новых начальных страниц используйте отдельный новый профиль.

Команда `Migrate legacy balance assets once` предназначена для перехода исходного проекта. Она отказывается перезаписывать уже мигрированную базу и не входит в обычное добавление контента.

## ID, профиль и ограничения

Текущий профиль версии7 хранит строковые ID, индексированные `WeaponMounts` с формами каждого крепления, экземпляры модулей, происхождение рисунка и версию свободных правил. Значения прежних `StructureKind`, `ChassisKind`, `TowerModules` и `DrawingPartKey` не перенумеровываются. Перестановка или переименование записей базы не меняет сохранённый состав. Подробная таблица v1–v7 и записи файла находится в [совместимости профиля](Content-Profile-Compatibility.md).

Неизвестный текущей базе ID в профилях v5–v7 сохраняется вместе с открытием, страницей, слотами, линиями и исторической оценкой. `Enabled=false` также сохраняет пользовательскую работу. Такая сборка недоступна для нового запуска или сохранения изменённого состава, пока автор не вернёт определение либо пользователь явно не заменит деталь. Автоматической подстановки, удаления страницы или возврата к первой детали нет. Для временного снятия с каталога предпочтительно отключить запись и сохранить её ID.

| Ограничение | Текущая граница |
|---|---|
| Крепления башни | До3, индексы0–2; основание задаёт свой `MountCount`. Первое обязательно; дополнительные могут быть пустыми. |
| Выбранные страницы | 4 слота. |
| Альбом | До64 страниц; ID страницы до64 знаков, имя до48. |
| Рисунок | До128 привязок, включая8 исторических; всего до128 штрихов и2048 точек на странице. |
| Новые bindings | Третье крепление и экземпляры оборудования делят общий предел128 привязок с8 историческими. Предел DTO экземпляров128 не увеличивает ёмкость рисунка. |
| Материалы | Существующие `Pencil`, `Ink`, `Marker`; значения настраиваются данными. |
| Цвета | `None`, `Red`, `Blue`, `Green`; эффекты существующих каналов настраиваются данными. |
| Роли врагов и прорисовки | Существующие `Doodle`, `Runner`, `Gnawer`, `Spitter`, `Brute`, `Bulwark` и `Sketch`, `Outlined`, `Hatched`. |
| Типы поведения | Закрытые наборы `AttackKind`, `EffectKind`, `ModifierStat`/операций/областей. Количество определений этих типов не привязано к enum деталей. |
| Файл профиля | До32MiB UTF-8; будущие схемы защищены от записи старой игрой. |

Новый алгоритм атаки, эффект с новым состоянием, характеристика оборудования, цветной канал или материал с новым поведением требуют C#-обработчика и проверки совместимости. После этого числовые варианты существующего обработчика снова задаются данными. Обычный вариант дальности, урона, темпа, конуса, рикошета, нагрузки или доступности требует только записи.

## Изменение assets и доставка игроку

Правка `.asset` в Unity влияет на следующую подготовку в редакторе. Уже собранный Player содержит свою сериализованную копию assets. Для доставки изменённого каталога нужен новый build или отдельно реализованный канал обновления контента. В этом проекте не добавлены runtime-загрузка удалённой базы, hot reload боя или импорт баланса из Excel.

`Paper Defense > Export mechanics and balance JSON` выгружает подготовленные Historical/Target. Прежние файлы `docs/balance` удалены при очистке: сначала выполните новый экспорт Unity, затем `Tools/BalanceWorkbook/Build.ps1`. Генератор создаёт Excel с механиками, балансом, формулами, каталогом и происхождением значений. Новые `docs/balance/balance-data.json` и книга — односторонний отчёт: они не заменяют Unity assets и не являются экспортом PlayerRules. База приёмки новых записей остаётся в `Assets/PaperDefense/Content/Acceptance`. [ContentAcceptanceRunner](../Assets/PaperDefense/Validation/ContentAcceptanceRunner.cs) и [ContentAcceptanceManifestAsset](../Assets/PaperDefense/Validation/ContentAcceptanceManifestAsset.cs) находятся в Editor-only сборке Validation; namespace сохранён после переноса из Application. Приёмка выполняется тестами без отдельной сцены.

Контракты подготовки и содержимого можно проследить по [ContentAssetBoundaryTests](../Assets/PaperDefense/Tests/Editor/ContentAssetBoundaryTests.cs), [ContentConfigurationBoundaryIntegrationTests](../Assets/PaperDefense/Tests/PlayMode/ContentConfigurationBoundaryIntegrationTests.cs) и [ContentDataOnlyAcceptanceTests](../Assets/PaperDefense/Tests/PlayMode/ContentDataOnlyAcceptanceTests.cs). Ссылки фиксируют существующие проверки кода; новый запуск тестов из этой страницы не следует.
